# RFC: AP2 v0.2 merchant authorization for published services

Date: 2026-08-13
Status: accepted
Deciders: Jason Colapietro

## Problem statement

Agent Studio exposes published services through direct HTTP, A2A 1.0
HTTP+JSON, MCP, and x402 v2. x402 authorizes and settles the payment rail, but
it does not provide a portable record of what a user authorized an agent to
buy. Agents need a deterministic authorization and evidence layer that binds
the selected service, exact input, immutable deployment, price, payee, payment
instrument, and resulting receipts without allowing an LLM to make a trust or
payment decision.

The current Agentic Payments Protocol is AP2 v0.2. It is early-stage, its
official A2A samples still target A2A 0.3, and its finalized x402 v2 binding has
not been published. Agent Studio must therefore support AP2 honestly without
claiming general AP2+x402 compliance or acting as a credential provider,
network, or merchant payment processor.

## Proposed solution

Add one code-owned, experimental AP2 v0.2 merchant profile to the canonical
published-agent run path. It applies to every published service, including
curated and customer-published agents, and is projected consistently through
Agent Cards, catalog/service metadata, OpenAPI, `llms.txt`, and payment docs.

Agent Studio owns these merchant responsibilities:

1. issue a short-lived ES256 merchant-signed Checkout JWT for an exact service
   call;
2. accept AP2 presentations only when the A2A AP2 extension is negotiated or
   the direct run request uses the documented AP2 header;
3. verify exact v0.2 Checkout and Payment Mandate schemas, SD-JWT disclosures,
   configured issuer trust, algorithms, time, audience, challenge nonce, key
   binding, delegation hashes, checkout hashes, and supported constraints in
   deterministic code;
4. bind the authorization to the canonical run URL, method, agent and slug,
   immutable Live deployment, canonical input digest, service schema, Base
   network, USDC asset, exact atomic amount, AP2 USD minor units, payee, payout
   address, and expiry;
5. reserve mandate and payment nonce identities durably before facilitator
   settlement so exact retries are idempotent and changed-body or concurrent
   replays fail closed;
6. call the existing x402 v2 verifier and facilitator only after AP2 succeeds;
7. sign AP2 Checkout Receipts for merchant acceptance or rejection, retain
   payment evidence returned by the settlement rail, and never claim that
   Agent Studio issued a protocol Payment Receipt unless it is operating the
   required payment-processor role.

The A2A extension URI is
`https://github.com/google-agentic-commerce/ap2/v1`. Agent Studio emits and
documents the A2A 1.0 `A2A-Extensions` header and temporarily accepts the
sample-client `X-A2A-Extensions` spelling. Mandates use the official sample
data keys:

- `ap2.mandates.CheckoutMandateSdJwt`
- `ap2.mandates.PaymentMandateSdJwt`
- `ap2.CheckoutReceipt`

Only exact schema identifiers are accepted:

- `mandate.checkout.1`
- `mandate.checkout.open.1`
- `mandate.payment.1`
- `mandate.payment.open.1`

The seller-defined AP2-to-x402 binding is explicitly advertised as
experimental. x402 remains the settlement rail and source of settlement
truth. AP2 adds authorization, request binding, replay protection, and a
merchant receipt; it does not replace the 402 challenge or facilitator.

## Trust and key configuration

AP2 is controlled by `AP2_MODE=off|optional|required`; absent or invalid values
resolve to `off`.

- `off`: do not advertise AP2 and reject any presented AP2 authorization.
- `optional`: advertise AP2 when all readiness checks pass. A request without
  AP2 may use the existing x402 path, but a presented invalid AP2 authorization
  never downgrades.
- `required`: advertise AP2 and require it for priced Live execution. Missing
  authorization, verifier/key-store failure, or replay-store failure stops
  before facilitator, provider, relay, or run creation.

Readiness additionally requires a P-256/ES256 merchant signing key with a
stable `kid`, a configured merchant issuer, at least one pinned trusted issuer
key, and durable replay storage. Root keys resolve only from the configured
issuer registry. Token-controlled `jku`, `x5u`, arbitrary JWKS URLs, embedded
root keys, symmetric algorithms, `none`, and unsupported constraints are
rejected. Key rotation is additive by `kid`; receipts remain verifiable through
the public merchant JWKS while their key is retained.

The Merchant Checkout JWT uses a randomized ES256 signature as required by
AP2. AP2 signing keys are separate from CDP/x402 wallet keys and are never
logged, returned, or passed into a workflow.

## Human-present and autonomous authorization

Human-present requests contain trusted-surface-signed closed Checkout and
Payment Mandates. They must carry the server-issued audience and one-time
checkout challenge and must match the current Checkout JWT.

Autonomous requests contain user/trusted-provider-signed open Checkout and
Payment Mandates with a `cnf` agent key, followed by agent-signed closed
mandates bound by `sd_hash` or `issuer_jwt_hash`. Every disclosed constraint is
evaluated. Agent Studio supports only the constraint families it can evaluate
against its signed checkout; unknown or stateful recurrence/budget constraints
fail with `unresolved_constraint` until their durable counters exist. Open-only,
closed-only, swapped, overlapping, or arbitrary multi-agent delegation chains
are rejected.

## Persistence and privacy

Add a dedicated append-oriented authorization ledger in both SQLite and
Supabase. Before settlement, an atomic unique reservation records only the
mandate reference, issuer, subject/payer identifier where disclosed, checkout
hash, canonical request digest, service/deployment identifiers, exact payment
terms, state, expiry, and sanitized decision code. Raw mandates, disclosures,
checkout JWTs, request bodies, payment signatures, risk data, and authorization
headers are never written to application logs or run inputs.

States distinguish `authorized`, `settling`, `settled`, `executing`,
`completed`, `rejected`, `failed`, and `pending_reconciliation`. An ambiguous
settlement never receives a fresh payment challenge and cannot fall back to a
second facilitator. A settled payment remains recorded when fulfillment fails.
Exact retries return the prior terminal response when available; a reused
mandate with a different request returns conflict.

Replay identity, payment terms, state, decision, deployment, run, and
transaction facts remain in the append-oriented ledger indefinitely. Bounded
terminal response evidence is a separate privacy lifecycle. The authenticated
cron scrubs `result_json` and nonessential signed receipt payloads only after
`AP2_TERMINAL_EVIDENCE_RETENTION_DAYS`; the setting accepts whole days from 7
through 365 and otherwise resolves to the conservative 90-day default. Cleanup
is limited to 100 rows per tick, is isolated from schedule execution, and never
touches `authorized`, `settling`, `settled`, `executing`, or
`pending_reconciliation` rows.

Scrubbed terminal rows retain the direct/autonomous mode, checkout and payment
references, and a SHA-256 reference to the signed Checkout Receipt (falling
back to the payment mandate reference when no receipt was issued). They also
retain an explicit `evidenceRetention.status = expired` marker. This keeps
replay prevention and settlement/fulfillment reconciliation durable without
retaining old response bodies or signed receipt payloads. An exact retry of a
scrubbed row remains terminal and must never settle or execute again; the run
route can identify the marker and return `410 ap2_terminal_evidence_expired`
instead of presenting a missing stored response as a retryable condition.

## Alternatives considered

### Advertise AP2 metadata without enforcement

Rejected. It would make crawlers believe services accept a protocol that the
runtime does not verify and would create a payment-authorization bypass.

### Treat x402 settlement as the AP2 Payment Mandate

Rejected. The artifacts have different roles, schemas, units, trust roots, and
evidence semantics. The current AP2+x402 v2 binding is not finalized.

### Implement credential-provider and payment-processor roles in Agent Studio

Rejected for this release. Agent Studio is the merchant and orchestration
surface. Those roles require separate regulated trust, credential-release,
network-verification, and Payment Receipt responsibilities.

### Accept self-asserted JWKs from callers

Rejected. A valid signature over an attacker-supplied key proves only that the
attacker signed its own token. Root issuer keys must be preconfigured.

## Risks and mitigations

- Protocol drift: pin the v0.2 `.1` schemas and identify the integration as an
  experimental profile. Unsupported versions fail closed.
- Replay or double settlement: reserve the mandate and EIP-3009 identity
  atomically before facilitator access and persist ambiguous outcomes.
- Price or service substitution: sign and re-verify one immutable checkout
  snapshot, including exact input and deployment digests.
- Algorithm or key confusion: allow ES256 only for merchant checkout signing
  and an explicit asymmetric algorithm allowlist per trusted issuer.
- Prompt injection: mandate and constraint evaluation is deterministic and
  occurs outside the workflow/LLM boundary.
- Privacy leakage: bound token and disclosure sizes, log hashes and decision
  codes only, never pass AP2 evidence into a workflow, and scrub terminal
  response/receipt payloads through the bounded retention cron while retaining
  replay and receipt references.
- Operational rollback: set `AP2_MODE=off`. Discovery and new enforcement turn
  off together while prior reservations and receipts remain readable for
  reconciliation and dispute.

## Success criteria

- All published services derive the same AP2 capability from the common run
  path; no curated, generic, slug, ID, A2A, relay, or company path bypasses it.
- A valid, trusted mandate binds exactly to the current signed checkout and
  x402 requirement before settlement.
- Missing, malformed, oversized, expired, unknown, mismatched, or replayed
  authorization never reaches facilitator, provider, relay, or run creation.
- Fifty concurrent retries for one mandate can produce at most one settlement
  and one execution; an exact retry is idempotent and a changed request
  conflicts.
- Signed Checkout Receipts verify independently and bind to the closed mandate
  hash on both success and AP2 rejection.
- No raw AP2 or payment evidence appears in logs or run inputs.
- Aged terminal response evidence is scrubbed without changing replay,
  settlement, state, run, or transaction facts; reconciliation states are
  never scrubbed and cleanup failure never blocks due schedules.
- Focused adversarial tests, the full test suite, TypeScript, lint, production
  build, independent security review, merged deployment, and exact-alias live
  discovery/dry-run checks pass before AP2 is advertised.
- No paid canary is performed without separate authorization.

## Decision record

Accepted. Agent Studio will implement the AP2 v0.2 merchant role for all
published services as an experimental authorization profile layered over its
existing A2A 1.0 and x402 v2 surfaces. The production rollout begins dark with
`AP2_MODE=off`; enabling `optional` or `required` is a separate configuration
step gated on keys, trusted issuers, durable storage, and the release checks
above.
